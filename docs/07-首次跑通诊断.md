## 1. 池子未截断到 maxCandidates

`poolSize: 501`，而 `cfg.pool.maxCandidates = 132`。旧版 `main.ts` 未引用 `cfg.pool`，
导致评估了全部 501 个，配额消耗约 4 倍于预算。

> 16:53 版已见 `selectObservationPool` / `assertPoolCapacity` / `candidateCount`，应已修复。
> **验收点**：`round_complete` 的 `candidateCount` 必须 ≤ `maxCandidates`。

## 2. 上游 55% 的 CA 根本没有 K 线 ⚠️ 数据现实

抽样 20 个 CA 拉 `range=24h` 的实测分布：

| 返回 | 占比 |
|---|---|
| `status="unavailable"`, `candles: []` | **11/20 (55%)** |
| `status="ok"`, 96 根 | 8/20 |
| `status="ok"`, 95 根 | 1/20 |

与全量的 336/501 = 67% 失败率吻合（老币/死币在上游无 K 线）。

**这不是 bug，是数据现实。** 但当前把它计入 `failures`，导致：
- 失败率虚高，淹没真正的故障信号
- 无法区分"这个币没数据"和"API 出问题了"

**建议**：`status === 'unavailable'` 单独计为 `noData`，不进 `failures`。
`failures` 只保留真实故障（网络、5xx、校验失败、429）。

## 3. RPS 全部为 null → A4 恒假 → 系统永不告警 🔴 最严重

39 条 evaluate 日志中，`rpsScores` 的五档**无一例外全是 `null`**。
由于 `A6 = A1 ∧ A2 ∧ A3 ∧ A4`，A4 恒假意味着**系统永远不会产生任何告警**——
`alerts` 表 0 行正是这个结果。即便 `breakout_moments` 已正确检测到 34 个创新高时刻。

**根因：`isFresh` 零容忍 + 全池拉取耗时**

```ts
export function isFresh(candles, intervalMs, now) {
  return candles.at(-1)?.openTime === Math.floor(now / intervalMs) * intervalMs - intervalMs;
}
```

要求最后一根收盘 K 线**精确等于**上一个周期起点，容忍度为零。而：

- 全池 501 个 CA 拉完耗时 **10 分钟以上**
- RPS 是相对排名，必须等全池数据齐了才能算，`now` 取的是**结束时刻**
- 于是最早拉的那批 CA，其数据已跨过 1–2 个 15 分钟边界 → `isFresh` 失败 → `continue` → 不进 `changes` → 该档 RPS 为空

单独验证：刚拉的单个 CA `isFresh = True`（相差 0 个周期），证明数据本身没问题，**是时间差造成的**。

**修复方向（三选一或组合）**：

1. **放宽容忍度** —— 允许 N 个周期的陈旧（建议配置化 `a4_rps.maxStalenessBars`，默认 2）。
   注意 RPS 是横向比较，各 CA 的端点应尽量对齐到**同一基准周期**，
   建议取全池最小的公共收盘周期作为基准，而非各用各的最后一根。
2. **拉取与评估解耦** —— 拉取时记录每个 CA 的数据时间戳，评估时以**基准周期**取价，而不是用 `now` 反推。
3. **缩小池子** —— 132 个 CA 的拉取耗时约为 501 个的 1/4，能显著缓解但不根治。

> 另外注意 `r288`/`r672` 依赖 1h 线补端点，而 `target` 按 15m 网格算，
> 只有当 `latest.openTime` 落在 `X:45` 时 target 才对齐整点。
> 其余 3/4 的时间窗口里，即使数据新鲜，这两档也取不到端点。这是独立于上面的第二个 bug。
