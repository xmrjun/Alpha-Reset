# 可行性与约束分析

> 基于 2026-09-11 对二娃 API 的实测。**开工前必读** —— 其中两项直接改变实现方案。

## 一、K 线粒度缺口 ⚠️ 最重要

API 的 `interval` 由 `range` 唯一决定，**无法自由指定周期**：

| 需求周期 | API 能否直接提供 | 方案 |
|---|---|---|
| **30 分钟** | ❌ **不提供** | 用 `range=24h` 的 **15m** 数据，**每 2 根合成 1 根 30m** |
| **60 分钟** | ✅ | `range=7d` → `interval=1h` |
| **4 小时** | ✅ | `range=30d` → `interval=4h` |

**30m 合成规则**：按 `open_time` 对齐到 30 分钟边界，`open` 取首根、`close` 取末根、`high` 取两根最大、`low` 取两根最小、`volume` 求和。

**容量刚好卡线**：`range=24h` 返回 96 根 15m = 48 根 30m，而需求 A3.2 要的正是「最近 48 bar」——**零余量**。任何一根缺失都会导致窗口不足，需在代码中校验 `len(candles) >= 96` 并在不足时跳过而非报错。

## 二、「历史新高」的数据边界 ⚠️ 语义塌缩

各周期实际能回溯的最长历史：

| 周期 | 数据来源 | 最长历史 |
|---|---|---|
| 30m（合成） | `24h` / 15m | **仅 24 小时** |
| 60m | `7d` / 1h | 7 天 |
| 4h | `30d` / 4h | 30 天 |
| 1d | `90d` / 1d | 90 天 |

**由此产生的问题**：

- **A3.1（30m 历史新高）与 A3.2（30m 最近 48 bar 新高）在现有数据下完全等价** —— 因为 30m 能拿到的全部历史就是 24 小时 = 48 根。两个条件塌缩成一个，对应的两条提醒文案（【30分钟历史新高回调提醒】/【30分钟一日新高回调】）将永远同时触发。
- A3.3 vs A3.4 正常（7 天 vs 48 小时，有区分度）
- A3.5 vs A3.6 正常（30 天 vs 8 天，有区分度）

**解决方案（建议采用第 2 条）**：

1. 降级：A3.1 改用 `30d`/4h 的最高价作为「历史高点」参考 —— 粒度粗，会漏掉 4 小时内的尖峰
2. **自建时序库**：项目本就每 30 分钟轮询一次，把每次拉到的 15m K 线落库累积，运行一周后即拥有真正的 30m 历史。**这是唯一能真正满足 A3.1 的方式**，且为后续回测提供数据基础
3. 接受塌缩，把 A3.1 与 A3.2 合并为一条规则（需业务方确认）

## 三、RPS 实现方案

RPS 只需要**区间首尾两个价格**，不需要窗口内每一根 bar，因此不必拉 15m 全量数据：

| 指标 | 回溯 | 取价来源 |
|---|---|---|
| RPS16 | 4 小时 | `24h`/15m，相隔 16 个周期的收盘价（连续数据需 17 根） |
| RPS56 | 14 小时 | `24h`/15m，相隔 56 个周期（需 57 根） |
| RPS96 | 1 天 | 相隔 96 个 15m 周期（需 97 根）；单次 96 根不足，依靠累积或精确小时端点 |
| RPS288 | 3 天 | 相隔 72 个小时的收盘价；小时线仅在端点精确对齐时可用 |
| RPS672 | 7 天 | 相隔 168 个小时的收盘价；单次 168 根小时线不足，需本地累积 |

**实现校正**：N 周期前不是包含当前根在内的倒数第 N 根，而是索引相差 N。
半小时刷新时，部分目标时间不在整点；不能拿邻近小时线近似 15m 的指定端点。
缺少精确端点时该周期记空，等待历史累积。

**注意池子定义**：需求明确「池子为观察组」。RPS 是**相对排名**，必须先算出观察组内**每一个** CA 的区间涨幅，再统一排序赋分。这意味着 **RPS 无法只对通过 A1/A2 筛选的子集计算** —— 否则排名基准就变了。这是配额预算的主要压力来源（见下节）。

存续不足的处理：按原文，代币存续时长覆盖不到某窗口时，该项 RPS 记空、不参与 A4 判定（不要当作 0 参与排名，会污染其他标的的分位）。

## 四、API 配额预算 ⚠️

### ⚠️ 免认证接口"不计配额"但**有账户级限流**（结论已修正）

**第一次的错误结论**：连续调 `binance/dexscreener` 20 次，`used_today` 不变 → 判定"免费随便用"。

**修正依据**：同机的 yaobi 项目（`/root/taoli/yaobi/docs/17-completeness-review.md`）记录了
**2026-09-01 事故** —— 行情轮询把日额度 24,251 用光导致**全站 429**，而那次打的正是
`binance/dexscreener`。结论：

> **计数器不统计 `binance/*`，不等于它没有限流。** 免 Token 的 `binance/*` 受账户级限流约束。

**因此**：`used_today` 不涨只说明它不占那个计数器，**绝不能据此无节制并发调用**。
按原计划"每轮 300 个 CA × 48 轮 = 每天 14,400 次 dexscreener"几乎必然复现该事故。

**强制要求**：
- 调用 `binance/*` **前后各读一次 `GET /api/v1/token/usage`**（yaobi 的既定做法），观察异常
- 遇 429 立即按 `Retry-After` 退避并持久化冷却状态，不要重试风暴
- dexscreener 调用量必须**按下节的缓存策略压到最低**

**免认证接口能提供**（不占 `used_today`，但受账户级限流）：

| 数据 | 字段 | 满足需求 |
|---|---|---|
| 交易对创建时间 | `pairCreatedAt` | **A1 上市时间** ✅ |
| 市值 | `marketCap` / `fdv` | **A2** ✅ |
| 流动性 | `liquidity.usd` | **A2** ✅ |
| 24h 涨跌幅 | `priceChange.h24` | **RPS96（1天档）** ✅ |
| 多窗口涨跌 | `priceChange.{m5,h1,h6,h24}` | 参考 |
| 多窗口成交量 | `volume.{m5,h1,h6,h24}` | 参考 |

**必须走配额的**：只有 K 线序列（`group_ca/board/ca/{ca}/kline`）——
A3 创新高检测、RSI、MA39、以及 RPS16/56/288/672 都依赖完整 K 线，快照替代不了。

⚠️ `GET /api/v1/binance/token/{ca}/info` 实测返回 **502**，不可用，别指望它。

### 关键优化：A2 根本不需要 dexscreener

`board/summary` 返回的 `cas[]` **本身就带 `latest_market_cap` / `liquidity` / `volume_24h`**，
3 次调用即可覆盖全池的 A2 判定 —— 无需为每个 CA 单独调 dexscreener。

dexscreener 唯一不可替代的是 **A1 的 `pairCreatedAt`（上市时间）**，
而上市时间是**永不变化的静态值** → **查一次永久缓存**，只对"本系统首次见到的新 CA"查询。

**调用量对比**：

| 方案 | dexscreener 调用量 |
|---|---|
| 原方案（每轮全池查） | 300 × 48 = **14,400 次/天** ❌ 必然触发限流 |
| **修正方案**（仅新 CA 查一次，永久缓存） | 每天新增 CA 数，**通常 < 50 次/天** ✅ |

### 分层架构（据此重做）

```
第 1 层（配额 3 次/轮）  board/summary × 3 群        → 观察池 CA 列表 N
        ↓
第 2 层（0 计数）        board/summary 已含市值/流动性 → A2 筛选（无额外调用）
                        dexscreener × 仅新 CA        → A1 上市时间，**永久缓存**
                                                     → RPS96 改用 K 线首尾价，不依赖 h24
        ↓
第 3 层（配额 M×n 次）   kline × M                   → A3 + 其余 RPS 档位
```

**关键**：K 线只拉通过 A1∧A2 的 M 个，不是全部 N 个。
A1∧A2（上市 >4h、市值 50k–40M、流动性 >30k）是相当严格的条件，M 通常远小于 N。

### 重算后的容量

沿用差异化刷新（24h 每轮 / 7d 每 2 轮 / 30d 每 8 轮）= 每 CA 78 次/天：

```
144（summary）+ 78 × M  ≤ 10500   →   M ≤ 132
```

**观察池 N 不再有硬上限**，受限的只是"同时满足 A1∧A2 的数量 M ≤ 132"。
N 的实际约束变成 dexscreener 的耗时：0.7s × N，300 个 CA 约 3.5 分钟，
30 分钟周期内绰绰有余，并发还能再压缩。

> 旧结论（池子上限 72 / 134）作废 —— 那是在"每个 CA 都拉 K 线"的错误前提下算的。

### RPS 的池子问题

需求要求 RPS 池子 = 观察组全体。分层后：
- **RPS96 用免费的 `priceChange.h24` 对全池 N 计算**，完全不耗配额，严格符合"全池"定义
- 其余四档（16/56/288/672）依赖 K 线，只能对候选集 M 计算 —— **这是对需求的偏离，需业务方确认**：
  是接受"其余档位以候选集为池"，还是必须全池（那就要对全部 N 拉 K 线，回到旧的容量限制）

### 配额保护

仍需保留：每轮前查 `api_usage`，85% 降级（跳过 7d/30d）、95% 停止并告警。

## 七、架构建议

```
┌──────────────────────────────────────────────┐
│  定时主循环（30 min）                          │
├──────────────────────────────────────────────┤
│ 1. board/summary × 3 群 → 观察池 CA 列表       │
│    （同时拿到 market_cap / liquidity → A1、A2）│
│ 2. 差异化拉取 K 线（24h 必拉；7d/30d 按缓存 TTL）│
│ 3. 落库：15m K 线累积存储 → 构建真实 30m 历史   │
│ 4. 计算：合成 30m → RSI / MA39 / 新高时刻      │
│ 5. 全池计算区间涨幅 → 排序 → RPS               │
│ 6. 判定 A6 = A1∧A2∧A3∧A4 → 小前提 → 补充标签   │
│ 7. 合并同一 CA 的多个标签 → 单条推送           │
│ 8. 去重（同 CA 同标签的冷却窗口）              │
└──────────────────────────────────────────────┘
        ↓ 落库                    ↓ 推送
   时序数据库                Telegram
        ↓
   alpha.0xdydx.top（暖色前端）
```

**关键点**：第 3 步的落库不是可选项 —— 它既是 A3.1 正确实现的前提，也是未来回测的数据基础。项目第一天就该开始积累。
