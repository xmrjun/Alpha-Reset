# K 线数据源

## 结论

**生产 K 线仅使用经过身份核验的固定 GeckoTerminal 序列，失败不回退拼接二娃或旧 candles。** 下文链覆盖及深度为换源时的样本记录，不保证每个池都有同样历史；当前契约见 [13-接入与口径修正.md](13-接入与口径修正.md)。

## 为什么换

最初用二娃的 `group_ca/board/ca/{ca}/kline`，实测 132 个 CA 里 75 个失败。
一开始误判为「上游约 55% 的 CA 没数据」，按链分组后真相完全不同 —— **有无 K 线是按链划分的**：

| 链 | 池中数量 | 二娃有 K 线 |
|---|---|---|
| **robinhood** | **271** | ❌ 0/4 |
| bsc | 115 | ✅ 4/4 |
| solana | 99 | ✅ 4/4 |
| *(chain 为空)* | 53 | ❌ 0/4 |
| ethereum | 37 | ✅ 4/4 |
| base | 15 | ✅ 4/4 |
| xlayer / hyperevm / tron / avalanche | 10 | ❌ 0 |

robinhood 是一条真实的 EVM L2（DexScreener `chainId=robinhood`、`dexId=uniswap`），
在池中占比最大。**排除这些链等于放弃池子里一半以上的观察对象**，
它们永远无法通过 A3（创新高、RSI、MA39 全依赖 K 线）—— 这不是可接受的取舍。

> `chain` 为空的 53 个是另一回事：实测是 `aaaaaaaa...`、无前缀 hex 之类的垃圾地址，
> DexScreener 也查不到，该排除。

## 为什么是 GeckoTerminal

| | GeckoTerminal | 二娃 |
|---|---|---|
| robinhood | ✅ 覆盖 | ❌ |
| 15m 深度 | **1000 根 ≈ 10.5 天** | 96 根 = 24 小时 |
| 1h 深度 | 1000 根 ≈ 41.7 天 | ~168 根 = 7 天 |
| 4h 深度 | 327 根 ≈ 54 天 | ~180 根 = 30 天 |
| 配额 | 免费，不占二娃额度 | 占每日 10500 |

**深度带来两个连锁修复**：

1. **A3.1 与 A3.2 不再塌缩** —— 30m 此前只能回溯 24 小时，恰好等于 48 根，
   于是「30m 历史新高」与「30m 最近 48bar 新高」永远同时成立，两条规则事实上合并。
   15m 有 10.5 天 = 500 根 30m 后，A3.1 才有真正的「历史」可比。
2. **r288 / r672 有机会直接取得端点** —— 必须实际存在统一 T 的精确收盘端点；小时线只能精确对齐补端点，不能容差匹配。

> DexScreener 也查过：**公开 API 没有 K 线端点**（candles 路径 404），
> 内部接口 `io.dexscreener.com` 返回 403（Cloudflare 拦截，需浏览器指纹），
> 不能作为生产依赖。

## 实现

**只拉 15m，30m/1h/4h 本地完整桶合成**。对全观察池持续串行 REST 采集；独立计算每 30 分钟的固定 T，不等待一圈请求完成，同 T 可接纳迟到端点修订。

```
board/summary（二娃，3 次/轮）→ 观察池
DexScreener 批量（免费）      → A1 日期 + 首次 pairAddress + chainId；A2 取 summary
GeckoTerminal（免费）         → 15m K 线 → 本地合成 30m/1h/4h
```

合成规则：**桶必须集齐才产出，残缺整桶丢弃**。半个桶算出的 high/low 会让 A3 的创新高判定失真。

## 限流

有效速率为配置与 10 req/min 中较低者；默认使用保守的公开免费端点上限。所有尝试（含重试）节流，网络错误、429、5xx 最多重试三次；按 Retry-After 退避，长冷却持久化到独立 gecko_cooldown。不得用旧的短时成功样本证明 20/30 req/min 长期可用。

132 个 CA 单次遍历的理论请求时间约 13.2 分钟，重试、上游慢响应和其他发现步骤会延长，不能保证一圈在 30 分钟内完成。计算和本地 WebSocket 推送独立于这段网络等待；降低覆盖只能形成待补范围，不能靠减少分母冒充完整排名。

## 错误码

`GECKO_INPUT` / `GECKO_HTTP` / `GECKO_RATE_LIMIT` / `GECKO_VALIDATION` / `GECKO_NETWORK`。

> 教训：最初 `GeckoTerminalError` 没有 `code`，调度器的 `failure()` 认不出来，
> 80 个失败全记成 `UNEXPECTED_ERROR`，完全看不出是限流。**错误分类要在第一版就做。**
