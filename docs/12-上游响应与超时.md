# 上游响应时间与超时设置

## 症状

前端显示「上次刷新 44 分钟前」，而策略本应每 30 分钟一轮；
观察池列表里 RPS 五档全部为空。

## 定位过程

日志里 `ERWA_NETWORK` 共 9 次，分布在 `usage`(3) 和 `board`(4)。
这两步都在轮次开头，**一失败即整轮中止**：

```
10 轮里 6 轮 evaluated=0
```

一开始按「偶发网络抖动」处理，加了重试和降级 —— 这是在给症状打补丁。
实际测量后发现根因完全不同。

## 实测数据

**网络层完全正常**：

```
ping juhequn.com   0% 丢包，RTT 9ms
DNS 解析           50ms
TLS 握手           0.12s
```

**上游响应时间极不稳定**（`board/summary`，days=5、limit=200）：

```
示例群组三    1.6s    9.0s    5.8s
示例群组一    1.4s    7.0s   41.0s
示例群组二   45.0s   45.0s   44.4s   ← 撞上测量时设的 -m 45 上限，真实更长
```

`token/usage` 这种轻量接口也会偶发变慢：10 次里 9 次在 0.3–0.8s，1 次 **9.8s**。

**且与数据量无关**：

```
示例群组二 limit=20  -> 16.7s
示例群组二 limit=200 -> 10.5s   ← 数据更多反而更快
```

说明是服务端实时聚合导致，耗时不可预测，不是传输问题。

## 根因

代码里认证请求的超时是 **15 秒**（`AbortSignal.timeout`），
而上游经常超过这个值。于是**正常但偏慢的响应被自己的超时掐断**，
抛 `ERWA_NETWORK`，整轮作废。

这个 15 秒是拍脑袋定的，从未对照上游的实际表现。

## 修复

1. **超时 15s → 60s**（对症）—— 依据是上述实测分布
2. **网络异常纳入重试** —— 原先只有 429/5xx 重试，超时直接抛出，两者同属临时故障，处理不一致
3. **配额查询失败改为降级而非中止** —— 远端 `token/usage` 只是监控动作，
   本地 `api_usage` 表一直在记账，足以支撑降级/停止判定

第 1 条是根治，后两条是兜底。

## 教训

- **先量,再改**。症状是「网络失败」，就很容易顺着「网络不稳」去加重试，
  而真正的问题是自己的超时设得脱离实际。
- **超时值必须有依据**。任何 `timeout(N)` 都应能回答「N 是怎么来的」，
  否则它迟早会以「偶发失败」的形式浮出来。
- **改完要部署**。本次修复后未立即重启服务，导致又跑了一个多小时旧代码，
  期间持续空轮 —— 验证「编译通过、测试通过」不等于「线上生效」。
